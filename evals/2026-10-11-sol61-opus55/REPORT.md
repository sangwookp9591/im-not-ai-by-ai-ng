종합 통과는 사전 고정한 사례별 요구 조건과 공통 의미 보존 계약을 함께 본 결과다. 사례별 좁은 체크리스트는 Sol 56/56 충족, Opus 55/56 충족·1개 보류다. Sol의 14번은 좁은 체크리스트를 충족해도 **원문에 없는 인과 추가** 때문에 공통 계약에서 실패했다. 단순 항목 수나 실행 성공률을 품질 점수로 대신하지 않았다.

시간은 CLI 시작부터 종료까지로 모델 추론·파일 읽기·도구 호출이 포함된다. 최대 4개 동시 호출, 캐시 상태와 런타임 차이가 있으므로 일반적인 모델 속도 순위로 확대하지 않는다. 응답 길이는 교정 본문뿐 아니라 설명·메모·마크다운을 포함한다.

이번 표본에서는 Opus의 최종 응답이 Sol보다 약 4.1배 길었다. 이것은 교정문 자체가 그만큼 길다는 뜻이 아니다.

## 실제로 발견한 문제

### 1. Sol: 자기소개서에 인과 관계 추가 — 수정 필요

원문은 두 사실을 따로 적었다.

> 저는 응답을 방문 전 확인 사항과 예약 후 변경 사항으로 나누어 정리했습니다. 팀 회의에서 예약 변경 안내를 먼저 보여주자는 의견을 냈습니다.

Sol 결과에는 다음 연결이 추가됐다.

> 이를 바탕으로 팀 회의에서 예약 변경 안내를 먼저 보여주자고 제안했고

정리한 응답이 제안의 근거였을 가능성은 있지만 원문은 이를 확정하지 않는다. ‘말투를 자연스럽게’ 만드는 과정에서 논리가 보강된 것이다. 결과의 검토 메모는 ‘추가 확인 사항은 없다’고 했으므로 자기검증도 이 추가를 놓쳤다.

두 모델에 후보 이름만 A/B로 제공한 독립 세션 교차 검토에서 모두 이 부분을 fail/major로 지적했다. **수정안:** ‘이를 바탕으로’를 제거하고 원문처럼 사실을 각각 서술하거나 사용자에게 실제 관계를 확인한다.

### 2. Opus: 기획서의 추측 표지 삭제 — 검토 보류

> 원문: 알림을 추가하면 처리 속도가 빨라질 수 있을 것으로 보인다.
>
> 결과: 알림을 추가하면 처리 속도가 빨라질 수 있다.

가능성은 남지만 ‘그럴 것으로 판단한다’는 유보 층위는 사라졌다. 자연스러운 중복 완곡 축약으로 볼 여지도 있어 사실 단정으로 바꾼 중대 오류와 동일시하지 않았다. 다만 현행 기본 계약은 추측 강도를 보존하도록 되어 있으므로 자동 채택 대신 검토 보류로 판정했다. 교차 검토 2차에서는 두 모델 모두 review/minor로 판단했다.

**수정안:** polish에서는 원문의 서법 구간 전체를 보존하고, 축약이 필요하면 별도 제안으로 제시한다.

### 3. Opus: 수정 없는 결과에도 설명과 확인 질문 과다

PPT 사례 03은 두 모델 모두 원문을 그대로 남겼지만, 최종 답변은 Sol 70자, Opus 832자였다. Opus는 보존 이유, 선택 제안, 통계 기준 확인, 화면 검증 한계 등을 덧붙였다. 기획 리뷰에서는 이런 상세함이 도움이 되지만 빠른 문구 교정에서는 요청보다 출력이 커진다.

잘 쓴 안내문 사례 12에서는 새 날짜 예시와 문법 설명까지 덧붙였다. 교정본 훼손은 없었으나 검토 범위를 넓혀 추가 확인 부담을 만든다. 대본 사례 07은 본문에서 3분 분량을 못 맞췄다고 정확히 밝혔지만 제목을 ‘발표 대본 (3분용)’으로 붙여 상태가 한눈에 일치하지 않았다.

**개선 제안:** polish 기본 출력은 교정본 + 중요한 이유 1~3개, 수정 없으면 원문 + 이유 한 문장으로 제한한다. 자세한 검토는 review 또는 사용자 요청에 맞춘다.

## 잘 작동한 부분

- 두 모델 모두 REQ-1~3의 의무/선택/금지와 긴급 요청 예외를 보존했다.
- PPT의 불릿·짧은 문구를 산문으로 늘리지 않았고, 내부 테스트/n=20을 화면에 유지했다.
- 근거 없는 ‘A안이 가장 저렴하다’를 문체 개선으로 덮지 않고 근거 부족으로 지적했다.
- 발표의 첫째/둘째를 유지했고, 정보가 부족한 3분 대본을 사실 창작으로 채우지 않았다.
- 자기소개서에서 개인의 일정 조율과 팀의 12명 인터뷰를 구별했다.
- 과거 처방 예시에서 빠졌던 ‘질’의 주장과 ‘아직 검증되지 않았다’는 조건을 모두 보존했다.
- 기본 스킬이 혼합 문서에서 슬라이드·발표 규칙을 실제로 읽고 구획별 적용했다.

## 사용 판단과 개선 순서

**현재는 검토를 거쳐 사용하는 파일럿에 적합하다. 무검토 자동 배포는 권하지 않는다.** 이번 표본에서 Sol은 일상적인 문체 교정에 더 짧고 빠르게 답했고, Opus는 상세 검토와 누락 확인에 강점을 보였다. 하지만 어느 모델도 공통 의미 보존 계약을 항상 지키지는 않았다.

1. 공통 계약에 ‘문장 연결을 자연스럽게 하려고 인과·대조를 새로 만들지 않는다’는 구체 사례를 추가하고, 접속어 추가 시 원문 근거를 대조한다.
2. 의무/가능/추측 구간을 통째로 보존하는 polish 원칙을 더 명확히 한다. 중복 완곡 축약은 검토 제안으로 분리한다.
3. 출력 길이와 확인 질문 수를 모드별로 제어한다. 미완료 상태가 제목과 본문에서 일치하게 한다.
4. 검토 메모의 ‘보존 완료’를 근거로 삼지 않고 원문↔교정본을 별도 대조한다. 실패한 13·14번을 회귀 사례로 유지한다.
5. 규칙 수정 후 같은 사례의 재검증과 새 사례 검증을 구별하고, 실제 개인 문체·팀 자료와 모델별 반복 실행을 추가한다.

이번 요청은 품질 평가이므로 **평가 대상 스킬은 수정하지 않았다.** snapshot의 해시도 실행 후 동일함을 확인했다.

## 평가의 한계와 실행 증거

- 14개 합성 사례 × 모델당 1회다. 통계적 우열이나 모든 실무 문서에 대한 신뢰도를 주장할 수 없다.
- 검사자는 현재 작업을 수행한 AI다. 독립 인간 평가나 전체 블라인드 평가를 수행하지 않았다. 문제가 의심된 2개 사례만 모델명을 가린 새 세션에서 교차 검토했다.
- 교차 검토 1차에서 발췌본의 검토 메모가 빠졌다는 잘못된 지적이 나왔다. 원래 전체 응답에는 메모가 있었다. 발췌 범위를 명시해 재실행했고, 1차의 해당 형식 지적은 판정에서 제외했다. 원문·1차·2차 기록 모두 보존했다.
- 후보 A/B 순서는 사례별로 뒤집었지만, 동일 모델이 자기 출력을 알아볼 가능성까지 배제한 실험은 아니다. 교차 검토는 보조 근거이고 최종 판정은 원문과의 대조에 따른다.
- 스킬 읽기를 명시한 호출이므로 자동 스킬 탐색 성공률 평가가 아니다. 무스킬 대조군도 없어서 스킬 자체의 인과적 개선 효과는 측정하지 않았다.
- CLI별 시스템 프롬프트·도구 환경이 다르다. 실제 팀 문서, PPTX 화면, 음성 낭독, 개인 말투 학습은 평가하지 않았다.
- Opus는 14개 응답의 modelUsage에서 claude-opus-5-5만 사용됐음을 확인했다. Sol은 로컬 모델 카탈로그, 명시 모델 ID 호출, 정상 응답으로 확인했다. Sol JSON 이벤트가 서버의 모델 ID를 별도 반환하지 않아 추가적인 서버 측 식별 증명은 없다. 자동 fallback 옵션은 사용하지 않았다.
- Opus 본 평가 14회 메타데이터의 API 정가 환산 비용 합계는 $1.2902다. 연결 확인과 교차 검토 비용은 제외했으며 구독 실청구액이 아니다. Sol 비용은 확인되지 않아 추정하지 않았다.
